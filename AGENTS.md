# Ритм: архитектура и проверка требований

Этот файл — путеводитель по готовому решению для разработчика и технического ревьюера. Сначала прочитайте [README](README.md): там запуск и адреса сервисов. Здесь собраны архитектурные решения, соответствие ТЗ и ссылки на доказательства реализации.

Ритм объединяет непрерывный приём телеметрии, прогноз задержки и рабочее место диспетчера. Сильная сторона проекта — полный проверяемый путь от бинарного NDTP-пакета до прогноза, объяснения и рекомендации, с общей семантикой времени и риска во всех модулях.

## Архитектура и ответственность модулей

```text
План и справочник ТС ───────────────────────┐
NDTP / декодированные сообщения / CSV ──────┤
                                          ▼
                              Backend: состояние парка
                              GPS → посещения → cur_dev_s
                              план + история на момент T
                                          │ HTTP /predict/batch
                                          ▼
                              ML: Transformer → prior → HGBR
                              задержка + вероятность + факторы
                                          │
                                          ▼
                              Backend: актуальность, алерты,
                              наблюдения и what-if
                                          │ /api/v1/state
                                          ▼
                              Дашборд: карта, карточка ТС,
                              рекомендации и журнал
```

- **Backend — FastAPI, порт 8000; NDTP/TCP — 9201.** [app.py](backend/app.py) задаёт API, [engine.py](backend/engine.py) хранит состояние, собирает входы модели и публикует результат. Источники сходятся в общем обработчике: архив проверяет тот же расчёт, который работает на живом потоке.
- **ML — отдельный FastAPI-сервис, порт 8001.** [app.py](ml_service/app.py) загружает модель один раз и обслуживает одиночные и пакетные запросы. [learned.py](ml_service/learned.py) объединяет frozen Transformer и HGBR. Backend обращается к нему по HTTP, что позволяет независимо обновлять модель и запускать несколько реплик.
- **BI-дашборд — отдельный nginx-контейнер, порт 8080.** [app.js](dashboard/app.js) обновляет карту и карточки из единого снимка состояния. Выбор автобуса, линия, предупреждения и рекомендации работают с одними идентификаторами и временем.

Состав сервисов, healthcheck, порядок старта и автоматический перезапуск заданы в [compose.yaml](compose.yaml). Python 3.12 и зависимости закреплены в [Dockerfile](Dockerfile) и [requirements.txt](requirements.txt). Запуск по README сразу использует поставляемый архив и готовую модель; её загрузчик проверяет SHA-256.

### Основные сущности и входные данные

Схемы находятся в [common/contracts.py](common/contracts.py), [common/state.py](common/state.py) и [backend/engine.py](backend/engine.py).

| Сущность | Смысл |
|---|---|
| `VehicleConfig` | Автобус `tr_id`, терминал `unit_id`, подпись и ссылка на линию |
| `Telemetry` | Координаты и скорость автобуса, время события и получения, источник, идентификатор сообщения; при наличии — состояние дверей |
| `StopTarget`, `ScheduledStop` | Конкретное плановое посещение: ID, координаты остановки и плановое время. ID посещения различает повторные приезды к одной остановке |
| `CurrentDeviation` | Текущее отклонение, его источник, время наблюдения и доступности; ссылка на посещение |
| `PredictionRequest`, `Prediction` | Зафиксированные входы на T и ответ модели: целевая остановка, секунды отклонения, вероятность, версия и объяснение |
| `VehicleView`, `DashboardState` | Оперативное состояние автобуса и согласованный снимок для интерфейса |
| `ForecastTrace`, `Incident` | Полный обмен с ML и сохранённое предупреждение с моментом выдачи, целью и ожидаемым прибытием |

**Координаты остановок загружаются из плана**, поле CSV `geom = POINT (lon lat)`. NDTP передаёт положение самого автобуса. Живой план и привязка терминалов принимаются через `POST /api/v1/live/context`; подтверждённые прибытия — через `/api/v1/arrivals`. Собственный архив загружается через `/api/v1/replay/import`: телеметрия и план обязательны, `points.csv` — дополнительный источник текущего отклонения. Точные схемы и примеры — в [контракте входов](docs/OPERATIONS.md#входные-данные).

### Как сообщение становится прогнозом

1. [NDTP-приёмник](backend/ndtp.py) обрабатывает handshake, CRC, фрагменты кадров, Nav00 и IRMA04. `Engine.on_nav` сопоставляет терминал с автобусом; `ingest` нормализует сообщения и устраняет повторы. [CSV replay](backend/replay.py) подаёт сообщение после `max(event_time, receive_time)`.
2. [GPSArrivalDetector](backend/gps_arrivals.py) сопоставляет последовательность точек с плановыми посещениями: учитывает геозону, порядок, направление подхода, скорость, несколько подтверждающих точек и выход из зоны. Проверки скачков, разрывов и повторных координат защищают привязку; доступные переходы датчиков дверей служат дополнительным сигналом.
3. `Engine.ingest_arrival` вычисляет **`cur_dev_s = arrived_at − scheduled_at`**. Новое посещение обновляет отклонение. Подтверждённое операционное прибытие может уточнить GPS-оценку. Само движение часов это значение не увеличивает.
4. `Engine.request_for(T)` выбирает первую плановую остановку в **`(T+10, T+15]` минут**. `features_at` и `delay_history_at` собирают только доступную к T историю. Прогноз пересчитывается в цикле backend по текущему снимку; события посещения и обновления прогноза имеют разную роль.
5. Backend отправляет запросы в `/predict/batch` порциями по 128, проверяет соответствие ответа запросу и сохраняет `forecast-trace`. Это размер пакета, а весь парк обрабатывается последовательностью пакетов.
6. Перед публикацией `gate_prediction` повторно проверяет актуальность. Новый красный алерт создаётся только в действующем целевом окне и один раз для пары «автобус — посещение». В журнале сохраняются время выдачи, граница использованных данных, плановое и ожидаемое прибытие.
7. Дашборд получает `/api/v1/state`, обновляет стрелки автобусов, карточку, список требующих внимания и журнал. Входы и выход последнего расчёта доступны через `/api/v1/vehicles/{tr_id}/forecast-trace`.

Такое разделение связывает каждое число с конкретным моментом и посещением. Горизонт контролируется и схемой запроса, и моментом публикации предупреждения; результат задержавшегося HTTP-запроса не создаёт алерт задним числом.

## Почему выбраны эти решения

**Гибрид вместо одной универсальной модели.** Transformer переносит динамику изменения задержки из 103 919 швейцарских последовательностей, а HGBR калибрует её по московскому расписанию и текущему состоянию. В бустинг поступают 13 признаков состояния/плана и один `neural_prior`. Компактный scalar prior позволяет использовать временную модель вместе с сильной табличной регрессией. ID нужны для поиска плана; признаки описывают положение и время. Архитектура, сравнения и первоисточники подробно разобраны в [ML.md](docs/ML.md).

**Единый контракт исследования и приложения.** [Frozen builder](ml_service/frozen_plan/plan.py), [манифесты](ml_service/artifacts.py) и проверка хешей фиксируют схему признаков и версии весов. Будущий план используется как известный план; история наблюдений ограничивается моментом T. Это позволяет проверять воспроизводимость отдельно от отображения.

**Интерпретация рядом с действием.** [diagnostics.py](backend/diagnostics.py) обнаруживает длительную стоянку, падение скорости, медленное движение и изменение отклонения. [explainability.py](ml_service/explainability.py) рассчитывает групповые Shapley-вклады, а [learned.py](ml_service/learned.py) — чувствительность Transformer к истории. Карточка показывает содержательные наблюдения и полезные факторы прогноза; what-if переводит предупреждение в конкретный вариант действий.

**География и модель имеют ясную ответственность.** GPS-детектор привязывает наблюдение к посещению, [segment_observations.py](backend/segment_observations.py) оценивает движение в коридоре планового перегона, [route-geometry.js](dashboard/route-geometry.js) строит линии по локальному кэшу из 835 дорожных сегментов OSRM. Карта не требует обращения к маршрутизатору во время работы. [line_identity.py](backend/line_identity.py) объединяет планы по устойчивому совпадению остановок: выбор автобуса выделяет всю соответствующую линию и её транспорт.

### Цвета и намеренный статус по умолчанию

Пороги заданы в одном [risk_policy.json](common/risk_policy.json): жёлтый — **60–150 с включительно**, красный — **больше 150 с**, синий в UI — опережение **больше 30 с**. С увеличением задержки красный становится бордовым. Backend передаёт политику интерфейсу, а ML и backend используют её через [risk.py](common/risk.py). Вероятность **`P(задержка > 120 с)`** — отдельный показатель; [probability.py](ml_service/probability.py) связывает калибратор с версией модели и происхождением входов.

**Автобусы, которые сейчас не трекаются или не имеют активной оценки, намеренно показываются зелёными с подписью «По плану»; в крупной карточке — «По расписанию». Это выбранное стандартное поведение интерфейса.** В [app.js](dashboard/app.js) за него отвечают `RISK.unknown`, `effectiveRisk`, `displayedDelay` и `delay`. Такой нейтральный статус оставляет визуальный акцент на действующих предупреждениях.

Расчётное состояние хранится отдельно: API сохраняет `unknown`, `prediction_availability` и `null` для отсутствующего числа; прежний расчёт остаётся в trace с собственным временем. Политика цвета не создаёт численный прогноз `0`, вероятность или обучающую метку. Это разделение закреплено в [проверках UI](tests/dashboard.test.cjs), [проверках доступности](tests/test_prediction_availability.py) и [проверках риска](tests/test_risk_policy.py).

## Дополнительные возможности

- **Сопоставление GPS с планом и дорожное отображение.** Детектор восстанавливает конкретные посещения по последовательности телеметрии; локальный OSRM-кэш делает траектории на карте читаемыми. Порядок остановок, направление и временная доступность учитываются непосредственно в обработке потока.
- **What-if «усилить линию».** [transfer_advisor.py](backend/transfer_advisor.py) ищет ближайший подходящий автобус с другой линии в радиусе 5 км при задержке выбранного ТС от 150 с. Сценарий оценивает время подачи, выигрыш на целевой остановке и затронутые посещения донора. Его параметры явны: коэффициент расстояния 1,4, скорость 20 км/ч, подготовка 120 с. Диспетчер получает сравнение и принимает решение. [Проверки расчёта](tests/test_transfer_advisor.py), [проверки интерфейса](tests/transfer_ui.test.cjs).
- **Оптимизированный инференс.** Веса загружаются один раз, Transformer работает в `torch.inference_mode()`, запросы объединяются в пакеты по 128. Несколько ML-реплик обслуживаются через gateway. Эти решения обеспечивают измеренную задержку на CPU и позволяют масштабировать вычислительную часть отдельно от состояния парка.
- **Гибрид нейросети и бустинга.** Transformer извлекает временной сигнал, HGBR учитывает локальный план. Обе части участвуют в итоговом прогнозе; grouped Shapley и анализ истории делают его проверяемым.
- **Контролируемое дообучение.** Подтверждённые live-прибытия связываются с сохранёнными прогнозами в SQLite. После накопления новых меток планировщик обновляет HGBR и проверяет кандидата по MAE на более поздних данных. Принятую версию выбирает оператор; включение описано в [OPERATIONS.md](docs/OPERATIONS.md#накопление-и-обновление-модели).
- **Удобная эксплуатация.** Свой архив CSV, полный и диспетчерский режимы, сворачиваемый список ТС на карте, строгие фильтры риска, экспорт предупреждений, просмотр входов и выхода ML через API. Некорректный импорт сохраняет текущую рабочую сессию.

## Основания для оценки по критериям

Основная шкала ТЗ — **26 баллов**. В таблице указан максимум каждого критерия и конкретные основания для его проверки.

| Критерий и максимум | Что предъявляет решение |
|---|---|
| **Точность — 6** | Командный конкурсный score **1.0**, выше порога 0,70 для 6 баллов. В [ML.md](docs/ML.md) приведены test MAE гибрида **65,053 с** и persistence **93,360 с**, исследование и выбор архитектуры |
| **Горизонт и раннее предупреждение — 4** | Окно `(T+10, T+15]` по плановому прибытию проверяется на входе ML и при выпуске алерта. Доступность истории, запоздалый ответ и уже достигнутая цель проверяются отдельно; trace и журнал фиксируют время и данные каждого решения |
| **Три модуля и Docker — 6** | Самостоятельные backend, ML и dashboard; проверенный запуск с train и validate; рабочий Swagger; официальный NDTP-эмулятор прошёл путь до HTTP learned-прогноза |
| **BI-дашборд — 6** | Карта с текущими ТС и цветами, понятная карточка с прогнозом и наблюдениями, предупреждения, поиск и фильтры, выделение линии, what-if и обновление вслед за потоком |
| **Производительность и надёжность — 4** | Измеренные p95, приём всех сообщений тестового потока, отсутствие незавершённых раундов в конце, проверка reconnect, повреждённых кадров и остановки/возврата ML |

Доказательства производительности в [verification.json](docs/verification.json): Docker Linux ARM64, **4 vCPU, около 6 ГБ RAM**, **40 автобусов и 40 сообщений/с**, **960/960** сообщений за 23,7 с. p95 от отправки NDTP до получения состояния через API дашборда — **1,62 с**, p95 HTTP-инференса — **333 мс**. Повторное подключение NDTP — **1,59 с**, переход на резерв при остановке ML — **0,49 с**, восстановление после запуска ML — **2,57 с**. Здесь явно заданы границы измерения: отправитель → API и HTTP-инференс.

Сохранённая проверка включает **776 Python-тестов и 129 JavaScript-проверок**: 85 основного интерфейса, 16 what-if, 15 карты парка и 13 геометрии. В ней также зафиксированы браузерные проверки на ширинах 1440, 900 и 390 px, собственный CSV и границы цветов 60/120/130/150/150,001 с.

## Короткий маршрут проверки

1. Выполнить команды из [README](README.md), открыть `http://127.0.0.1:8080`, нажать «Продолжить».
2. Выбрать автобус на карте: проверить прогноз, линию, наблюдения и what-if при подходящем состоянии. Открыть журнал и экспорт предупреждений.
3. Открыть `http://127.0.0.1:8000/docs` и `http://127.0.0.1:8001/docs`. Посмотреть `/api/v1/state`, `/api/v1/metrics` и `forecast-trace` выбранного ТС: один запрос показывает весь путь входов и результата.
4. По [JURY.md](docs/JURY.md) подать официальный NDTP либо собственный CSV. Нагрузку и восстановление повторяет `python tools/check_docker_load.py --check-recovery` в тестовом окружении; параметры стенда описаны в `--help`. Этот сценарий временно переключает контекст и останавливает/запускает ML, затем возвращает архив на паузу.
5. При изменении кода запустить соответствующие тесты из `tests/`; для полного прогона в тестовом окружении — `python -m pytest -q` и четыре файла `tests/*.test.cjs` через Node. Команды запуска и эксплуатации поддерживать в README/JURY/OPERATIONS, результаты — в артефактах проверки.

## Правила внесения изменений

- Работать непосредственно в `main`. Писать коротко, по-русски; архитектурные объяснения держать здесь, детали ML — в ML.md, команды эксплуатации — в OPERATIONS.md.
- Сохранять контракт времени: и событие, и получение должны быть доступны на T; будущие фактические прибытия не входят в признаки. Сохранять отдельные сущности плана, текущего отклонения, прогноза и представления UI.
- Сохранять намеренное зелёное представление «По плану» без активной оценки и исходную семантику API. Пороги менять только через общий `risk_policy.json` с проверкой backend, ML, UI и what-if.
- Результаты измерений связывать с их сценарием и артефактом. После изменения поведения проверить затронутые тесты; после изменения запуска или интеграции — соответствующий путь Docker.
- В Git разрешены пять CSV для запуска: `dataset/train/traffic.csv`, `dataset/train/schedule.csv`, `dataset/validate/traffic.csv`, `dataset/validate/schedule_plan.csv`, `dataset/validate/points.csv`. Другие исходные данные, веса, секреты, локальные пути и журналы GPS в Git не добавлять. Модель распространяется через GitHub Release; настройки загрузки — [config/model-release.json](config/model-release.json).
